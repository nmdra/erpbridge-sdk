# Plan: ERPBridge SDK (TypeScript) — v0.1.0

## Goal

Ship a **TypeScript client library** (`@erpbridge/sdk`) that gives application and AI-agent developers a single, ergonomic way to consume an ERPBridge server — MCP tool calls, REST tool invocation, log aggregation, metrics, cache, and health — **without hand-rolling JSON-RPC, SSE parsing, or retry logic**. Authentication support ships in a separate future plan (see D17) once the server's own auth lands.

For whom: developers embedding ERPBridge into agentic-AI workflows, web backends, and monitoring tooling (the audience the docs site already targets in `docs/sdk/overview.mdx`).

Why: today the only options are bridgectl (a CLI) or copy-pasting the hand-rolled client examples in `docs/erpbridge/mcp-client-guide.mdx`. Neither provides a library that handles typed results, session reconnects, and typed REST wrappers.

Decisions confirmed with user: **TypeScript** (v1), **wrap the official MCP client** (`@modelcontextprotocol/client@~2.0.0`, aligned to the server's mcp-go spec), **auth deferred to a future plan**, REST surface = **logs + metrics + health + cache + tool registry + direct invoke**, repo at **`~/Documents/Projects/erpbridge-sdk`**.

### External research (TS SDK practices, 2025–2026, verified 2026-08-20)

- **Build tooling**: tsdown (Rolldown-based) is the fast-growing successor to tsup and is what the official MCP TypeScript SDK v2 builds with (`format: ['esm','cjs']` + `fixedExtension`, PR #2405); tsup remains the battle-tested fallback with a compatible API in v0.22.x (PkgPulse comparison, pkgpulse.com/guides/tsup-vs-tsdown-vs-unbuild-typescript-library-bundling-2026). tsdown auto-generates `exports` and integrates publint/attw validation (tsdown.dev/guide).
- **MCP SDK split (v2)**: `@modelcontextprotocol/sdk` v1 is monolithic — the client drags in server deps (express, hono, cors, npm registry). The v2 line splits into `@modelcontextprotocol/client`, `@modelcontextprotocol/server`, `@modelcontextprotocol/core`; `client@2.0.0` is client-only, Node >= 20, ESM-first + CJS, deps: zod, jose, cross-spawn, eventsource, eventsource-parser, pkce-challenge (npm registry, checked 2026-08-20).
- **Dual ESM/CJS**: canonical 2026 manifest = `"type": "module"` + `exports` with `types` nested first in each `import`/`require` branch, `.mjs`/`.cjs` + `.d.mts`/`.d.cts`, legacy `main`/`module`/`types` fallbacks (Node docs nodejs.org/api/packages.html; MCP client package.json as the working example). One shared `.d.ts` for both branches leaves CJS consumers wrong-typed under `node16` (javascript-package-publishing.com). `require(esm)` stable in Node 25.4.0 (2026-01) makes ESM-only defensible later, but dual remains the enterprise-safe default (SnipShift 2026-07).
- **Types/config**: author for `module/moduleResolution: nodenext` (the only correct module options for Node libs — typescriptlang.org modules reference); `verbatimModuleSyntax` + `isolatedModules` (+ `isolatedDeclarations` TS 5.5+) are the recommended library flags; run `tsc --noEmit` as a separate typecheck gate (js-package-publishing).
- **Source maps**: ship `declarationMap` **only if `src/` ships too** (go-to-def lands on missing files otherwise); plain `.js.map` is bloat for unminified output (web-standards.dev 2026-08).
- **Metadata**: `files` allowlist (`["dist","src"]`), `sideEffects: false` only when truly side-effect-free, SPDX `license`, `engines` advisory, `./package.json` exported for tooling (npm docs; webpack tree-shaking guide).
- **Subpath exports** are the SDK norm (MCP v2 ships `.`/`./stdio`/`./validators/*` with a runtime-neutral root — ts.sdk.modelcontextprotocol.io/v2/get-started/packages.html). Cautionary tale: MCP SDK v1.29.0's exports map pointed at files missing from the tarball, breaking root import (issue #2273) — tarball-level validation is mandatory.
- **Versioning/release**: for a standalone package with 1–2 maintainers, **release-please** (PR-driven, human gate, composes with npm publish) beats changesets (monorepo-first by design — changesets/docs/decisions.md) and semantic-release (no review step, tag on every merge) (latchkey.dev, tenki.cloud 2026 comparisons).
- **npm publishing**: **Trusted Publishing (OIDC) is GA since 2025-07-31** — no `NODE_AUTH_TOKEN`, provenance automatic for public repos; requires npm >= 11.5.1, Node >= 22.14, GitHub-hosted runners, and the package to already exist on npmjs.com; `repository.url` must exactly match the GitHub repo (github.blog changelog 2025-07-31; docs.npmjs.com/trusted-publishers/).
- **CI shape**: Node LTS matrix (`lts/-2`…`lts/*`), `npm ci`, separate lint/typecheck/test/build jobs; top-level `permissions: contents: read`; SHA-pin all third-party actions (GitHub's allowed-actions policy can block unpinned actions since 2025-08-15); Dependabot for `github-actions` + `npm`; no caching in release builds (docs.github.com secure-use; npm trusted-publishers example).
- **Publish gates**: `npm pack --dry-run --json` file assertions + **publint** + **attw --pack** (they catch different failure classes — publint.dev/docs/comparisons) + `npm audit --audit-level=high` AND **osv-scanner** (different advisory feeds; union is the finding set) — on PRs and a scheduled nightly scan (google/osv-scanner-action).
- **Docs deploy**: official chain `actions/configure-pages` → `upload-pages-artifact` → `deploy-pages` on the `github-pages` environment with `pages: write` + `id-token: write`; separate workflow from release; not a `gh-pages` branch push (docs.github.com Pages custom workflows; k0swe PR #820).

## Scope

**In (v1, TypeScript):** `createClient(config)` + capability groups (MCP tools, REST wrappers, config); typed errors; `node:http` fixture tests + gated live integration suite; dual ESM+CJS build via tsdown with subpath exports; `0.1.0-alpha` milestone after assembly; release-please + npm trusted-publishing pipeline; GitHub Actions CI/release/docs workflows with publish gates; README; docs-site `docs/sdk/*` pages; CHANGELOG.

**Out (v1):** Python/Go ports; **auth (token resolution, bearer injection, `ERPBridge_TOKEN`, scope awareness) — deferred to the future `.agents/plans/Plan-auth.md`**; token management (create/revoke); stdio transport in the SDK (agents use server stdio directly); `erp.`-prefix normalization; `/api/cache/list|inspect`; codegen of typed tool signatures from JSON schemas (manual proxy is enough for 16 tools); `docs/sdk/authentication.mdx`. Publishing is wired for OIDC but the first release still needs a bootstrap token (package must pre-exist on npmjs.com — see Open Questions).
